## 1 · What the earlier audits did not look at

Each of these was found by an incident, not by an audit.

### 1a · Background tasks die silently, and nothing restarts them

`_supervise()` (F-2026-08-31-01) reports a dead loop; it does not restart
it, and it wraps only three loops. Measured with an AST walk of every
`while True` and every `create_task`:

| task | supervised | one exception ends it |
|---|---|---|
| `broadcast_logs` - feeds every packet to registry, map, stats, silence, propagation | **no** | the trackers are guarded since v3.2.160; the rest of the body is not |
| `_persist_loop` - checkpoints, uptime, missing list | **no** | branches guarded individually |
| `_silence_watch_loop`, `_monitor_loop`, `_ai_analysis_loop` | yes (report only) | watch loop guarded; the other two are not |
| `fixed_beacon._beacon_loop` | **no**, reference dropped | yes: `_send_beacon()` unguarded |
| `ai_gateway._status_loop` | **no**, reference dropped | yes: `int(cfg[...])` on a live-edited setting |
| `extension_server._serve` | **no**, reference dropped | - |

F-2026-10-07-04 is this class: one exception in `broadcast_logs`, twelve
hours of a connected agent counting nothing.

### 1b · The agent's own health reaches nobody in time

- The agent knows when it is deaf (`[silence] feed deaf since ...`) and says
  so only in its log.
- The outside check (`uptime.yml`, cron every 10 min) **did** catch the 12 h
  outage: runs at 13:49Z and 19:35Z failed with "feed not moving". But
  GitHub ran it 12 times in 3 days, every 3-6 h, and its only channel is
  e-mail.
- `aprs-update.sh` declares `Deploy OK` when `/api/status` answers. It said
  so for v3.2.158, whose agent stopped processing 14 s after start.

### 1c · The host's reboot path was never tested

Unattended upgrades reboot the host automatically at 03:30. The first such
reboot after the panel software was installed is what came up without a
network (F-2026-10-07-02). The cause is fixed; the path has not been
exercised since. Details outside the repository.

### 1d · Checks use synthetic packets and miss real branches

`check_unheard_time` ingested packets only from gates nobody had heard, so
the propagation branch that `prev` broke never ran. The raw feed is on the
host (`packets.log*`, ≈ 37 h), and a replay through the live code was built
twice (F-2026-10-06-02, F-2026-10-08-01) - and thrown away twice. Its
fidelity is now measured: 30 openings replayed against 27 live in the same
hours.

### 1e · Recovery had never been tried

Backups were integrity-checked, never restored. Done today: they restore
and load (§0). The PC pull failed on the outage morning with an unhelpful
PowerShell message and does not retry within the day.

## 2 · Findings by area

### 2a · Judgement pipelines

- **Silence alerts per day:** 118, 105, 140, 148, 164, 168, 134 (09-28 to
  10-04), 114, **81** after v3.2.150, 788 on 10-07 (776 of them false,
  F-2026-10-07-02). The -35 % of the 10 min hold holds.
- **Missing list:** 1,601 entries, median age 12.9 days, p90 51.5, **341
  over 30 days**. By design entries leave only when heard (operator's
  decision, F-2026-10-05); the default view is the last 7 days.
- **Propagation:** suspect links are 42 % of flags (343 of 344 position
  jumps); the 250 km floor adds 70 % of openings on the same hours
  (F-2026-10-08-01, corrected).
- **Notification delivery is not auditable:** a successful Telegram digest
  leaves no log line. The two digests of the network-less morning failed on
  DNS - which is why 776 false alerts never reached a phone. Luck, not
  design.
- **`silence_history_void`** keeps every voided row with no retention
  (24,073 now). The 23:50 void end of F-2026-10-07-05 also took 2 correct
  rows written by v3.2.161 - as expected, negligible.

### 2b · Security

Fine: admin path redirects to login; the public port refuses writes (404 on
POST); config 600, directory 750; no secrets in any tracked file (pattern
scan); certificates renew. Open, low: the public page still listens on all
interfaces behind the firewall (AUDIT-2026-09-15 item 15). Host items
outside the repository.

### 2c · Dependencies and platform

17 packages behind, none with an advisory (Dependabot 0). Majors held:
openai 3, multidict 7, websockets 16. **Python 3.10:** every current release
still supports it, but most have now raised their floor to exactly 3.10, so
the next majors are where it drops. The 2026-09-07 decision (move when a
dependency drops 3.10) stands; the move should be prepared before that day,
not on it.

### 2d · Data

DB 97 -> 108 MB in a day, the void table and a day's history. Retention:
silence history 14 days, packet logs ≈ 37 h (5 × 200 MB rotation) - long
enough for a replay of the last day, not of a week.

### 2e · Performance

Nothing measured is slow (§0). The 7.85 s registry rebuild tail of F-36
(AUDIT-2026-08-15 §7) was not reproduced in today's samples; not
investigated further. Restart churn is the real cost: each start waits 15
min before the first silence scan, rebuilds caches, and - as 2026-10-07
showed - is where regressions surface.

### 2f · Records

- HANDOFF's "repo HEAD" row is one paragraph of thirty releases; the
  "running" row carries a day's incident history. Both are hard to read
  cold.
- NEXT's status block is headed 2026-09-29.
- **HELP.html says nothing about how an alert is decided** - no 3× interval,
  no 10 min hold, no 24 h window, no deaf or after-a-break state, no
  propagation floor (0 mentions of each).
- Windows download v3.2.130, 32 tags behind; the gap includes the two
  regressions of 2026-10-07, which never reached it.

### 2g · Interface (screenshots of the public map, 800×600 and 375×812)

- **The world view does not fill the map:** dark bands left and right on
  desktop, a 280 px band above the tiles on a phone.
- **The description line is clipped** mid-second-line on both.
- **On a phone the map starts at y ≈ 365 px of 812**: header, tabs and three
  status strips come first.
- The stats bar wraps with its fifth tile alone on a phone.
- Half the propagation lines are grey suspect ones (§2a).
