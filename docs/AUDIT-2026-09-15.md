## 1 · Security

### 1a · aiohttp 3.14.1 — three advisories, one of them server-side

| advisory | side | fixed in |
|---|---|---|
| CVE-2026-69243, request smuggling through WebSocket upgrade | **server** | 3.14.2 |
| CVE-2026-59881, RSV1 frames decompressed without negotiation | client | 3.14.2 |
| CVE-2026-69244, out-of-bounds read building a parse error | client | 3.14.3 |

aiohttp is the process that serves the public page and `/ws`. It sits behind
Apache and nginx, which may normalise the smuggling vector, but that is not a
reason to keep a known server-side parser bug. **The Windows build already
ships 3.14.3**; only the VPS lock is behind.

Cost: one constraint line, one tag, a deploy. Nothing in the code changes.

### 1b · cryptography 46.0.7 — four advisories, blocked by one pin

Name-constraint bypass in the certificate verifier (CVE-2026-69248), an
exponential blow-up resolving malformed chains (CVE-2026-69249), a PKCS#7
decryption oracle (CVE-2026-69247), and a vulnerable OpenSSL statically linked
into wheels before 48.0.1.

The only thing that pulls it in is `atproto` (the Bluesky extension), and
**atproto 0.0.69 caps it at `<47`**, so the fix cannot be taken on its own.
atproto 0.0.70, 0.0.71 and 0.0.72 all raise the cap to `<51`. The two move
together. The Windows build pins cryptography 45.0.7 and is affected too.

Cost: two pins, and the Bluesky extension has to be exercised afterwards,
because atproto is 0.0.x software and minor releases are allowed to break.

## 2 · Data that is being lost

### 2a · Propagation openings dropped on a locked database

Four openings in 24 hours never reached `prop_history`, so they are absent from
the timeline and from `find_prop_event`:

    01:36:50  [prop] OPENING EM: 2 links from 2 senders, max 2934.1 km
    01:36:56  [prop] history write failed: database is locked

Each failure lands about six seconds after its OPENING line. That matches the
cause: `record_prop_event` opens `sqlite3.connect(path)` with Python's default
**5-second** busy timeout, while the database runs in rollback-journal mode
(`journal_mode=delete`), so any writer holding the file blocks it. This is not
one call site. **14 of the 16 `sqlite3.connect` calls** in `station_db.py`,
`web_gui.py` and `main.py` carry no timeout; the two that do use 120 s.

The fix is one connection helper used everywhere, with a timeout long enough to
outlast the longest writer. WAL would remove reader-writer blocking entirely,
but it changes the file set (`-wal`, `-shm`), which every copy and backup
procedure then has to know about. Take the helper first and see whether locks
still occur before reaching for WAL.

### 2b · No backup of the database exists

No cron entry, no copy under `/var/backups`, no second file anywhere on the
disk. `/etc/aprs-agent/aprs_stations.db` holds the station registry, fourteen
days of silence, propagation and hazard history, and the message history. A
nightly `sqlite3 .backup` with seven kept copies costs a few hundred megabytes
and no application change.

## 3 · The error counter is almost entirely one false alarm

**Telegram.** `getUpdates` asks Telegram to hold an idle long poll for 10 s,
and `_tg_api` gives the HTTP read 15 s. A five-second margin is not enough, and
every overrun is logged as an error. That is all 72 error lines of the day. It
is also why the error count shown to the operator reads as alarming while
nothing is wrong.

Fix: give the read the poll timeout plus a generous margin, and treat a read
timeout on an idle long poll as the normal outcome it is. Cost: a few lines in
`telegram_ext.py`.

**Silence AI notes.** Twelve assessments hit the 20-second read timeout. Each
one is a note the operator never sees. The call already runs in the
background, so a longer timeout costs nothing but a later note — but measure
the provider's latency for a week before choosing the number.

## 4 · Owed measurements, taken today

### 4a · Hazard correlation — above chance, too few episodes to decide

Due since 2026-09-09.

**The query written into HANDOFF cannot give a base rate.** `silence_history`
stores only alerting snapshots: all 22,285 rows carry `alert = 1`, so filtering
on it selects everything. The meaningful population is the snapshots in cells
that also broadcast hazards — 17 cells, 693 snapshots.

| window against a warning in the same cell | snapshots | share |
|---|---|---|
| within 2 h | 57 of 693 | **8.2 %** |
| shifted +24 h | 10 | 1.4 % |
| shifted −24 h | 9 | 1.3 % |
| shifted +72 h | 27 | 3.9 % |
| shifted −72 h | 17 | 2.5 % |

The real window beats every shifted control, by two to six times. But the 57
snapshots collapse to **six episodes in five cells** (`DM52`, `EL19`, `EM30`,
`EN12`, `EN55`), counting snapshots more than six hours apart as separate
episodes. Six episodes is not a result in either direction.

**It cannot simply be left to ripen.** Every history table keeps
`_HISTORY_RETENTION_S = 14 days`, so the window never grows past what is
measured here. Either extend retention for the two tables involved, or record
episode counts outside the database at a fixed interval and accumulate them.

## 5 · Dependencies and platform

`pip check` is clean. Twenty-four packages have newer releases. Most are patch
bumps. The ones that are not:

- **openai 2.45 → 3.14.** A major version, but the Windows build already ships
  openai 3.0.0 and is published, so the single call site in the AI gateway is
  known to work on 3.x.
- **cryptography 46 → 50** — see 1b.
- **websockets 15 → 16**, pulled in transitively.

`requirements-lock-linux.txt` was captured on 2026-08-12 and should be
regenerated from the VPS after any bump, exactly as its header describes.

**Python 3.10.12.** Deciding not to upgrade was settled on 2026-09-07 and is
not reopened here: Canonical maintains 22.04's 3.10 into 2027, and 3.10 is the
interpreter that surfaced the cross-loop lock bug 3.13 would have hidden. The
python.org end of support in 2026-10 is not the trigger. The trigger is a
dependency dropping 3.10 wheels, and the 1a/1b bumps are where that would first
show.

**Memory.** Two samples seven minutes apart both sit below the recorded peak,
so there is no evidence of monotonic growth. There is no evidence against it
either, because nothing records RSS over time. One journal line a day would
settle it.
